# 发布机制：蓝绿 / 灰度 / 金丝雀（v0.1 方案）

> 2026-08-12 果总授权制定。原则：简单优先（全量复制一份资源），高级机制（云服务版本管理）逐步引入。
> 果总：OSS 版本管理天然支持蓝绿；PG 本身不支持，需切换库方式；最简单 = 全量复制一份资源。

## 一、分层方案

| 层 | 发布机制 | 说明 |
|----|----------|------|
| **OSS 静态站点**（studio 前端） | **蓝绿 = OSS 版本控制** | 启用 Bucket Versioning，发布前自动备份（历史版本），出错恢复历史版本；发布 = 上传新版本 + CDN 刷新（现有 deploy-studio 流程已含） |
| **FC 服务**（provider 后端） | **蓝绿 = 新版本函数 + 别名切换**；**金丝雀 = 别名按比例引流** | 每次发布保留上一版本镜像 tag（蓝）；新版本部署到别名（绿），验证后切换 100%；FC 3.0 支持按版本/别名路由与灰度流量百分比 |
| **PostgreSQL 数据** | **全量复制（简单优先）** | 发布前 `pg_dump` 全量备份；破坏性变更：新库（复制）→ 迁移应用 → 验证 → 切换连接；**生产数据库保护**（果总唯一强调）：任何破坏性操作前必须备份 + 回滚预案 |
| 回滚 | 上一版本镜像 tag + 数据备份恢复 | 发布流程默认保留上版本（镜像 tag 不覆盖），配合数据备份即可回滚 |

## 二、操作规范（当前可执行）

1. **发布前**：`pg_dump` 生产库全量备份（存 OSS 指定前缀 `backups/<service>/<date>/`）
2. **发布中**：镜像 tag 用版本号（不覆盖旧 tag）；FC 更新后验证 healthz + 关键 API
3. **验证**：新版本健康检查 + 核心流程冒烟（如支付：充值→扣费→对账）
4. **失败回滚**：重发上一版本 tag（镜像未覆盖即可恢复）
5. **金丝雀（可选）**：FC 别名设置灰度流量（10% → 50% → 100%），灰度观察期验证

## 三、数据库备份脚本（生产保护）

```bash
# 全量备份（发布前必做）
pg_dump -h <rds> -U <user> <db> | gzip > /tmp/<db>-<date>.sql.gz
aliyun oss cp /tmp/<db>-<date>.sql.gz oss://quanttide-terraform-state/backups/<service>/<date>/
```

> 注意：RDS 内网，备份需在 VPC 内执行（FC 临时函数或跳板）；v0.1 起至少保证**发布前备份**。

## 四、成熟度路线

| 阶段 | 能力 |
|------|------|
| v0.1（当前） | 版本 tag 保留 + 发布前 pg_dump 备份 + 失败重发旧 tag |
| v0.2 | OSS 版本控制启用（蓝绿前端）；FC 别名 + 金丝雀引流 |
| v0.3 | 数据迁移自动化（新库复制 + 切换脚本）；发布流水线集成备份/回滚 |
